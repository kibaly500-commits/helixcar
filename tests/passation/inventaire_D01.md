## Risques

Retirer ou renuméroter l'étape 1 en intégré risque de casser _peutNaviguerVersEtape, la délégation de clic sur #client-step-indicator (13371) et les classes hc-step-count-4/5.
- Garde précoce contre le flash : un script dans <head> qui pose hc-integre avant le parsing doit conserver la condition « encadré » (window.parent !== window), sinon ouvrir index.html?integre=1 à la main efface la vitrine (t_demande_integree D5).
- Écran de complétion : le rapatrier dans le shell (iframe ?completer=&integre=1) implique de réutiliser postMessage et de garder t_infos B1-B14 (exécuté sur index.html?completer=) ; supprimer la redirection dashboard 3114-3116 sans remplacer l'entrée URL casse ces tests.
- Sauvegarde progressive : autoriser un envoi partiel côté écran est sans risque serveur (repondre_informations_demande ignore les vides) mais change le message de confirmation attendu par t_infos B10/B11 (« bien été enregistrées », zéro champ restant).
- Regroupement par véhicule : reposer sur le préfixe `vehicule_<rang>_` des clés (101:178-236) ; les demandes historiques sans fiche véhicule utilisent les clés plates (101:242-273) et doivent rester traitées. - Compteur « Demandes de devis » : deux formules (serveur PostgREST, local _estDemandeDeDevis) doivent rester strictement équivalentes ; t_stabilisation 790-824 les vérifie partiellement. Tout nouveau badge côté client (« Informations à compléter », « À évaluer ») doit être calculé depuis le serveur, jamais codé en dur comme `badge: 1`.
- Évaluations : brancher la page impose une table + RLS (propriétaire de la mission uniquement, une évaluation par mission, lecture admin) et une lecture réelle des missions du client — aujourd'hui inexistante côté client ; le retrait de la bannière avant branchement ferait échouer t_nettoyage_dashboard B12/B13.
